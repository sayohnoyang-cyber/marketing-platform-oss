# 活动统计、预测、限流与预热

实施日期：2026-11-11。对应原型最终版的活动入口、预测、开场检查、开场看板、复盘和短链管理。页面沿用现有原型样式，操作接真实接口。

## 数据库与部署

升级已有库按顺序执行至 `V009__refund_amount_attendance.sql`，随后重启后端。空库按 README 执行 V001—V009。没有引入自动数据库迁移框架，不能反复执行增量脚本。

- `campaign_operation` 保存预测快照、预热执行和限流策略，按商家和活动隔离。
- `(activity_id, kind, request_key)` 唯一；相同请求重试复用记录，变更参数或活动配置须使用新请求标识。
- 预热执行令牌防止接管后旧执行者覆盖结果；RUNNING 超过30秒没有心跳时，同一请求可接管并重新执行安全任务。
- 配置指纹包含活动版本、状态、时间、预算、主链、券规则、投放数量与限领，以及渠道标识和开关。不含已领量和访问量，领取本身不会让准备结果过期。
- 修改配置后旧快照和预热记录会返回 `stale=true`。限流策略过期或与配置不符时回落到默认保护额度，运营可重新应用或明确停用。
- `marketing.capacity.deployment-id` 默认 `local-single`。硬件、实例数、资源配置变化时应更换此标识，旧基线将不可用。

## 访问统计

公开跳转和活动入口统一使用服务端签发的 `marketing_visitor` HttpOnly Cookie。客户端传入的 `visitorId` 或 `X-Visitor-Id` 不作为统计身份。过滤常见 bot/spider/crawler/slurp User-Agent；这不是完整的反作弊系统。

活动有效访问是合法活动入口产生的访问记录，按浏览器访客去重。停用、未知来源和常见爬虫不计数。活动总数在活动范围去重，各来源在来源范围去重；同一浏览器先后访问两个渠道时，全场1人、各渠道各1人，不能直接把渠道UV相加当作全场UV。旧的 `landing`、`anonymous` 常量身份不纳入有效访客数。

短链统计来自既有 Outbox 的访问事件和访问明细。按短链去重后汇总为“全部短链有效访问”，同一浏览器跨短链分别计数。异步投递可能延迟；它与活动落地页到达是不同观测点。预热不会调用公开跳转或生成访问事件，后台沙箱也不会写统计。

- `GET /api/merchant/links/stats`：当前商家所有未回收短链的PV/UV与口径说明。
- 活动列表、详情、`report`、`dashboard`、`review` 已返回真实 `visits`。
- 管理界面来源明细中的预约、领取、核销和退款计数继续来自真实业务记录。
- 当前为累计统计，暂未增加日期范围筛选或分时趋势页面。Cookie被禁用或清除会影响访客去重。

## 预测快照与容量

- `GET/POST /api/merchant/activities/{id}/forecasts`：读取最近20次快照或保存服务端计算结果。
- 保存参数：`requestKey`、按渠道ID/`direct`索引的`arrivalRates`、`growthPercent`、`attempts`、`scenario`、`unreservedQps`、可选`baselineId`。
- 预约人数由服务端查询，不能从客户端伪造。停用渠道不计入预计到场；未预约流量通过额外QPS明确输入。同时统计活动有效访客数 `totalVisits`、访问→预约转化率与基于未预约访客推算的参考QPS；尚无预约但已有有效访问量时，`plan` 会将该参考QPS纳入容量风险评估。
- 窗口10秒：`Σ(来源预约 × 到场率) × (1 + 增长率) × 人均尝试 / 10`。
- 三场景再乘以1.0/1.8/2.8并叠加未预约QPS。系数和到场率是运营假设，不是统计置信度。库存不截断预计需求。
- 快照固定当时预约、参数、配置指纹、模型版本、生成时间和容量引用。页面能恢复历史参数，并区分当前估算与已保存结果。
- JSON报告包含参数、结果、来源、容量和是否保存的信息。

`GET/POST /api/merchant/capacity-baselines` 用于录入可追溯的领券接口压测报告，当前商家可选最近50项。要求测试至少30秒和1000样本、P99不超过1000ms、错误率不超过1%、样本数与稳定吞吐基本匹配、测量时间不在未来、有效期不超过测量后7天。安全容量为 `max(1, floor(实测QPS × 0.8))`。

报告由运营录入，系统检查格式、部署匹配和有效期，不能独立证明报告真实性，也不会自动把演示值当作实测。多活动同时运行和其他接口的总压力仍需场景压测，单活动结果不是整个平台的容量承诺。

## 生效限流

- `PUT /api/merchant/activities/{id}/rate-limit-policy`，参数`requestKey`、`forecastId`。
- `GET`读回当前策略；`DELETE`明确停用。
- 只能从当前配置下已保存、关联有效容量报告的预测生成策略。Redis不可用时不应用策略。
- 总额度取场景需求与安全容量中的较小值；渠道按预计到场占比分配，未知/零占比来源只保留最小额度。
- 真实领券校验访问凭证后立即限流，早于活动、渠道、投放查询和领取意向写入；使用同一Lua原子检查活动总额与来源额度。计数窗口使用Redis时间，切换渠道不能绕过活动总额。
- 没有生效策略，或策略因配置、部署变更、基线过期而失效时，回落到默认保护额度 `marketing.capacity.default-claim-qps`（默认每场每秒200，0为关闭），不再拒绝全部领取。
- 限流判定在本机缓存 `marketing.capacity.policy-cache-ttl`（默认3秒），应用或停用策略时立即失效；多实例下其他节点最多延迟一个缓存周期。
- 超限返回HTTP429，错误码`A000008`。限流先于幂等查询，已成功的请求在超额时重试也会收到429，券已在券包中，稍后重试返回原券，不会重复发券。
- 固定自然秒窗口在边界允许突发；当前覆盖活动领取，不替代网关层全站防护。

## 真实预热

- `POST /api/merchant/activities/{id}/prepare-runs`，参数`requestKey`。
- `GET .../prepare-runs`读取最近20次；`GET .../prepare-runs/{runId}`读取指定执行。
- 原`preparation-runs`路径作为同一执行接口别名保留，已移除原先无动作的NOT_READY占位。

六项任务逐项持久化开始时间、结束时间、状态与说明：

1. 活动/券关系和发布条件校验。
2. 实际跳转缓存与布隆读回，不生成访问事件，不强制重建未恢复的布隆。
3. 券展示规则缓存写入与读回，不混用库存Hash。
4. 库存缓存预热与核对。若库存键尚未初始化，使用 `SET NX` 写入扣除在途 `RESERVED` 票据后的可用剩余并读回验证（发布活动时也会静默预热）；若已存在则只读比对，发现可能的在途预扣记 `UNVERIFIED`，不覆盖运行中库存。
5. 当前活动版本的展示读缓存准备与读回。公开页面仍以数据库的动态状态为权威。
6. 关联容量报告并检查可用性；根据有效访问量、预测峰值与安全容量输出分级预热强度（`STANDARD` / `ELEVATED` / `PEAK_PROTECT`）和保护建议（如开启限流或使用异步领券）；没有消息消费吞吐/积压排空实测时返回UNVERIFIED，绝不把未接监控写为成功。

执行结果可能是SUCCEEDED、PARTIAL、FAILED或STALE；单项另有SKIPPED和UNVERIFIED。部分完成可以安全重试。预热本身不修改基础设施规模、库存、发布状态或消费并发。

## 名称与自定义标识

普通短链新增`name`、可选`shortUri`；自定义后缀为2–12位字母或数字，留空仍生成6位随机码。公开解析、查询与创建保持一致，冲突返回409，不覆盖其他链接。

渠道创建新增可选`channelCode`，同样使用2–12位字母或数字；唯一性在活动内保证，留空由系统生成。前端创建弹窗与活动配渠道页均已接入。

## 2026-11-14 历史到场率、退款金额和消息观测

### 历史到场率

`GET /api/merchant/activities/{id}/forecast-calibration` 读取当前工作空间最近90天、最多20场同类型已发布活动。排除当前活动、未经过完整开场10秒窗口的活动、其他工作空间与其他类型。

分母是开场前有效预约的人数（开场后取消仍属于开场时的预约群体）。分子是这些用户在开场10秒内有合法活动访问或成功领取的人数。一个用户多次访问只算一次，跨渠道回访仍归入原预约来源。匿名回访仅在Cookie能关联同场开场前已绑定用户的访问时识别；换设备且未登录的访问不能强行归为已到场。公开入口现在可读取有效登录身份，失效或缺少登录仍允许匿名访问。

优先按渠道名称匹配历史，直接访问单独匹配；不足20人时使用同类型活动的工作空间汇总；再不足则默认40%，`source=DEFAULT` 且 `usable=false`。新预测自动采用可用历史到场率，已有快照不自动覆盖；“使用历史数据”可明确重新应用，滑杆仍能手动调整。增长率、重试次数、集中系数仍是人工假设，没有宣称整个预测模型已自动训练。快照保存当时的 `historyReference`，导出也保留参考数据。

### 退款金额

V009在 `voucher_redemption` 增加 `order_amount`、`refund_amount`、`refunded_at`。锁券记录真实传入的订单金额，同一订单重试不能改变金额。`POST /api/user/vouchers/{id}/refund` 新增可选 `refundAmount`，按现有整单退券语义要求等于订单金额减优惠金额；支持0实付的整单退券，不支持部分退款、多次退款或支付渠道操作。

旧调用省略金额仍兼容，但保留“待补录”，不把优惠金额当现金退款。具备订单金额的新结算可在退款后用同一接口补录一次金额，不重复退券、不新增转化事件。金额重复传入须一致；历史结算缺少订单金额时不推算。

活动与来源报表关联归因退款和对应结算，返回 `knownRefundAmount`、`unreportedRefunds` 和 `refundAmountStatus`。全部金额齐全时 `refundAmount` 为合计（无退款时为0）；任一笔缺失时为null，界面显示已知金额与缺失笔数。`GET /api/user/vouchers/{id}/redemptions` 只允许券所属用户读取最近50笔结算。我的券改用订单金额输入和整单退款记录弹窗，移除了写死的100元。

### 消息观测

`GET /api/merchant/activities/{id}/message-status` 返回当前活动的应用Outbox待发、发送中、已发待回执、重试、死信、超时发送及最近5分钟处理量。覆盖本场领券、核销、退款、转化投递和当前主链的访问统计事件。核销/退款须具备coupon-event和campaign-conversion两个回执；转化投递须具备campaign-report回执，不将Broker发送成功视为消费者完成。

按完整回执的事件去重计数，返回 `observedPerSecond`、`estimatedDrainSeconds`、`oldestPendingSeconds`；无处理样本时排空估算为null。近5分钟平均处理速度不是最大承载容量。`capacityVerified=false` 保持明确；这些指标不是Broker真实队列深度，也不代替部署压测。失败或超时消息会让预热容量项失败，其余情况下缺容量数据仍为未验证。

开场和预热页面展示消息状态，可见时每10秒刷新，页面隐藏暂停刷新。预热成功任务的技术细节移入悬停提示，仅失败任务展开原因。RocketMQ模式补齐 `campaign.conversion` 订阅及其死信订阅；本次开发环境仍使用本地投递，未宣称真实Broker已验收。


## 预约驱动的开场准备

`GET /api/merchant/activities/{id}/opening-plan` 返回当前预约驱动的开场评估，读取受活动归属校验保护，不创建预测快照。与保存预测使用同一计算过程：开场10秒内预计到场 × 人均尝试 ÷ 10 × 集中系数 + 未预约额外QPS。不按优惠券库存截断请求需求。

优先沿用已保存参数；尚无保存记录时采用可用的历史到场率，样本不足使用默认40%。新增预约会触发 `reservationsChanged` 与 `forecastNeedsRefresh`，配置变化或容量报告失效也会要求更新。旧快照保留其原始参数与记录，不静默覆盖；使用者通过“更新预约”和“保存预测”确认新结果。

- `reservationCount`：当前有效预约；`eligibleReservations`：当前启用入口对应的预约。
- `expectedArrivals`：增长和到场率假设下，启用入口在开场10秒内的预计到场人数。
- `peakQps`：所选场景的领券请求峰值估计，不是实测QPS。没有可用预约且没有输入额外请求量时为null。
- `capacityStatus`：NO_SAMPLE（待积累预约）、NO_ACTIVE_ENTRY（已有预约入口待启用）、UNVERIFIED（容量未验证）、OVER_CAPACITY（预测超过容量）、WITHIN_CAPACITY（按当前假设在容量范围内）。
- `nextAction`：积累预约/配置渠道、更新预测、评估容量、执行预热、查看开场或复盘。活动开场后及结束后优先引导相应看板。

总览、预测页、预热页共享评估口径；预测页未保存的高级参数变更会在前端即时估算并显式标记待保存。预热实际准备缓存、券规则及库存，并检查消息情况，不自动扩容，也不把容量未验证改为已就绪。
