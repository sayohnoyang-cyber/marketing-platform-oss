# 活动投放、主链与发布检查

核对日期：2026-11-10。功能以工作台设计原型（V14）为准，模块边界以架构约定为准。本文记录工作台原型与早期活动实现之间的差异。预测、预热和复盘在后续阶段实现，原型里的演示 QPS 不作为真实容量。

## 和现有实现的差异

| 主题 | 已有 T08 | 新版原型要求 | 本阶段方案 |
| --- | --- | --- | --- |
| 券和活动 | `campaign_offer` 只保存模板编号 | 同一模板可给多场活动，每场单独投放数量和限领 | 券模块新增 `offer_inventory`。活动只保存投放编号，通过接口分配、追加、回收和领取 |
| 库存 | 领取直接扣模板 `stock` | 发行总量、未分配、各场已领和剩余分开，且不能超额 | 模板 `stock` 改为未分配量。`issue_total` 为发行总量。投放数量从中划出 |
| 限领 | Redis 计数按模板 | 一场跨渠道共用限领，不同场不能共用计数 | 本场计数键 `coupon:alloc-user:{user}:{allocation}`。模板计数键保持独立。两次计数都通过才发券 |
| 幂等 | 请求唯一键是用户、模板、请求号 | 不同投放的同一请求号不能互相挡住 | 唯一键加上 `allocation_id`。直接领取用 `0`。预扣键带投放编号 |
| 渠道 | 每个渠道一条短链 | 一场活动一条主链，渠道共用短码并带渠道参数 | `campaign_activity.main_link_id`。渠道只保存 `channel_code`。短链管理改的是同一条主链 |
| 直接访问 | 没有 | 不带渠道参数算直接访问 | 访问和预约的渠道可空。空渠道记为直接访问 |
| 发布 | 只检查是否挂了券 | 时间、券、投放、主链、预算、基础准备都要在服务端再验一次 | `GET .../checks` 返回逐项结果。`POST .../publish` 再跑同一套，不看前端按钮 |
| 预算 | 无 | 投放数量乘单张最高优惠，不能用估算 | 核销规则必须有 `capAmount`。折扣券没有这个上限就不能发布 |

## 数量守恒

`issue_total = 未分配 stock + Σ 投放 quantity + 直接领取张数`

- 创建模板和追加发行量时，`stock` 与 `issue_total` 一起增加。
- 分配、追加从 `stock` 划入投放 `quantity`，不改变 `issue_total`。
- 开场前可以减少投放，减少的部分回到 `stock`。条件更新要求减完后不少于已领张数。
- 活动领取只增加该投放的 `claimed_count`，不扣模板 `stock`。
- 直接领取仍只扣未分配的 `stock`。
- 结束或下线时，未领完的数量回到 `stock`，投放 `quantity` 收成已领张数并冻结。已领的券继续按原核销规则使用。

分配、追加、回收都用 `offer_plan.inventory_qty` 或 `offer_inventory.quantity` 的条件更新。同一幂等键重复提交返回原结果；参数不一致返回冲突。

## 限领

本场限领只统计该 `allocation_id`。模板 `maxClaimsPerUser` 统计该模板下直接领取和所有投放。领取必须同时满足两个上限。本场限领不能高于模板总限领。用户券的 `claim_seq` 仍在模板维度递增，并在落库事务内通过 `FOR UPDATE` 取当前最大序号加一分配，避免 Redis 并发乱序回补限领计数后触发 `(user_id, plan_id, claim_seq)` 唯一键冲突。

## 开场前后

- 开场前：可以设置投放数量、减少未领数量、修改本场限领。
- 开场后，包括暂停：只能追加投放，不能减少，也不能改限领。售罄后追加，活动仍在进行中时入口恢复为可领。
- 结束或取消：冻结投放并退回未领数量，不能再领。

第一版一场活动只绑定一张券。更换只允许在开场前，且还没有已领张数。

## 主链和渠道

主链在短链模块创建，幂等键 `act:{activityId}:main`，落地页是 `{publicBase}/a/{activityId}`。渠道推广地址是同一短码加上 `c={channelCode}`。跳转使用 302 和 `Cache-Control: no-store`，查询参数按已有 `?` 决定接 `&` 还是 `?`。

主链停用时，短链记录和活动开关一起关掉，所有渠道和直接访问都不可用。单个渠道停用只影响该渠道。普通短链不走活动解析。

入口根据主链开关、渠道开关、服务端时间和投放剩余返回 `RESERVE`、`CLAIM`、`SOLD_OUT`、`ENDED` 或 `UNAVAILABLE`。预约和领取只接受服务端签发的访问凭证，不接受客户端自报渠道。

## 发布检查

每一项包含 `code`、`passed`、`reason`、`fix`。`fix` 只是后台步骤名：`info`、`pick`、`link`。正式发布失败时返回未通过项，不改活动状态。

检查项：活动时间、券归属和有效期、投放数量与限领、主链已启用、最大让利不超过预算。没有渠道也可以发布，直接访问仍可用。不要求已有预约预测。

## 迁移

不改 `V001` 到 `V004`。新增 `V005__allocation_main_link.sql`：

- `offer_plan.issued_total`，按当前库存加已发用户券回填。
- `offer_inventory`、`offer_inventory_command`。
- `claim_ticket.inventory_id`、`alloc_claim_seq`，唯一键改为含投放。
- `issued_voucher.inventory_id`。
- 活动主链、预算、渠道可空、访问和预约渠道可空。
- 去掉 `campaign_channel.link_id` 的唯一约束，因为渠道共用一条主链。

已有活动如果只挂了模板、没有投放，发布检查失败，直到补上投放和预算。已有渠道短链保留，入口仍能按旧 `link_id` 识别；新渠道不再各建一条短链。

## 任务顺序

1. 投放和领券。
2. 主链、渠道分支、直接访问。
3. 发布检查、预算、入口状态。
4. 后台页面对接这些接口。
5. 上述验收之后才做统计、预测和预热。
